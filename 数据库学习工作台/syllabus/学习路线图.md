## 学习闭环：不要只往前做，要回头巩固

```
做题 → 答错自动进错题本 → 答对排入间隔复习（1 / 2 / 4 / 7 / 15 / 30 / 60 天）
            ↓
诊断：按知识点标签算掌握度 → 指出薄弱块 + 推荐重点练哪几题
            ↓
阶段全部通关 → 解锁对应融合题（必须综合前 N 阶段才能做出来）
```

| 能力 | 命令 | 要点 |
|---|---|---|
| 今日复习 | `python run.py review --do` | 到期顺序：错题未攻克 > ❗标记 > 间隔到期 > 融合题解锁 |
| 错题重做 | `python run.py wrong --do` | 含最近一次的错误原因与当时写的 SQL；做对后自动移出 |
| 薄弱诊断 | `python run.py diagnose` | 输出「先补哪块 + 重点练哪几题」 |
| 解题思路 | `python run.py step <题号>` | 一次只给一步，最后一步教你怎么验证，**不剧透答案** |
| 笔记与标记 | `python run.py note <题号>` | ⭐收藏 / ❗易错（立刻进复习队列）/ ✓已掌握 |
| 标记笔 | 网页端选中文字 | 划重点 + 写批注，可 `python run.py notes -o notes.md` 导出 |

**推荐使用节奏**：每天新做 2~3 题，再花 10 分钟清掉复习队列。
复习队列空的时候，去做一道解锁的融合题检验综合运用能力。

## 阶段 1 · 查询基础（8 题 / 52 分）

**知识点**
- 子句书写顺序 vs 逻辑执行顺序
- `DISTINCT` 作用于整行组合
- `IS NULL` / `IS NOT NULL`，三值逻辑
- `LIKE` 的 `%` `_`，前导通配符为什么会让索引失效
- 日期用**半开区间** `[start, next)`，不要 `BETWEEN` 到 23:59:59
- `CASE WHEN` 短路、`COALESCE`、整数除法要写 `100.0`
- 多列排序、NULL 排序位置、`NULLS LAST`

**对应题目**：S1-Q01 ~ S1-Q08

**自测清单**（不看答案能答出来才算过）
1. 说出 `SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT` 的**逻辑执行顺序**。
2. `WHERE city <> '北京'` 会不会漏数据？漏哪些？
3. 为什么 `created_at < '2026-07-01'` 比 `BETWEEN ... AND '2026-06-30 23:59:59'` 更可靠？
4. `COUNT(1)` 和 `COUNT(*)` 有没有性能差别？

## 阶段 2 · 聚合与分组（7 题 / 59 分）

**知识点**
- `COUNT(*) / COUNT(col) / COUNT(DISTINCT col)` 的语义差别
- 聚合函数忽略 NULL；`SUM/AVG` 全 NULL 组返回 NULL，`COUNT` 返回 0
- `WHERE`（分组前过滤行）vs `HAVING`（分组后过滤组）与下推优化
- 条件聚合 `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`
- `SELECT` 列表必须全部出现在 `GROUP BY` 或被聚合（各库行为差异）
- 派生表做二次聚合；整数除法陷阱

**对应题目**：S2-Q01 ~ S2-Q07

**自测清单**
1. LEFT JOIN 之后数子表行数，为什么不能写 `COUNT(*)`？
2. MySQL 开启 `ONLY_FULL_GROUP_BY` 后，`SELECT city, COUNT(*) FROM customers GROUP BY status` 会怎样？SQLite 呢？
3. `AVG(x)` 的分母包含 NULL 行吗？想让 NULL 按 0 算怎么办？

## 阶段 3 · 多表连接（7 题 / 54 分）

**知识点**
- 显式 `JOIN ... ON` vs 逗号式连接（后者忘写条件 = 静默笛卡尔积）
- `INNER / LEFT / RIGHT / FULL` 语义边界
- LEFT JOIN 后加 `WHERE 右表列 = ?` 会退化成 INNER JOIN
- 反连接三件套：`LEFT JOIN + IS NULL`、`NOT EXISTS`、`NOT IN`（有 NULL 陷阱）
- 自连接必须起别名；`manager_id` 自引用树
- **行数膨胀**：主子表 JOIN 后 `SUM` 被放大，先降粒度再连接

**对应题目**：S3-Q01 ~ S3-Q07

**自测清单**
1. 一笔含 3 条明细的订单与明细表 JOIN 后，`SUM(total_amount)` 被放大几倍？怎么修？
2. `NOT IN (SELECT col FROM t)` 在 `col` 含 NULL 时结果是什么？为什么？
3. 多表查询报 `ambiguous column name` 的根因与修复方式。

## 阶段 4 · 子查询与 CTE（7 题 / 84 分）

**知识点**
- 标量子查询（返回一行一列）可作值使用
- `EXISTS` 半连接天然去重且短路；`IN` vs `EXISTS` 的取舍
- 关联子查询：外层每行执行一次，N 大时应改窗口函数
- 派生表 vs CTE：把「聚合结果」当表用，做分层统计
- `WITH RECURSIVE`：锚成员 + `UNION ALL` + 递归成员，必须能收敛
- 递归生成日历表，为缺失月份补零

**对应题目**：S4-Q01 ~ S4-Q07

**自测清单**
1. 递归 CTE 漏写终止条件会发生什么？各库的兜底参数叫什么？
2. 什么时候该把关联子查询改成 JOIN？看 `EXPLAIN` 里的什么信号？
3. 计算环比时，用自连接（`a.m = b.m - 1`）和用 `LAG()` 相比，执行成本差别在哪？

## 阶段 5 · 窗口函数（7 题 / 82 分）

**知识点**
- 窗口函数在 `GROUP BY / 聚合` 之后、`ORDER BY` 之前执行 → 必须先 CTE 再开窗
- `ROW_NUMBER / RANK / DENSE_RANK` 的并列行为差异
- `LAG / LEAD` 同环比，注意 `NULLIF(分母,0)` 防除零
- `ROWS`（物理行）vs `RANGE`（值域）窗口帧的区别
- `SUM(x) OVER ()` 全窗口 → 算占比；`PARTITION BY` → 组内占比
- 每组去重取一条：`ROW_NUMBER() = 1`，**必须加第二排序键**保证确定性

**对应题目**：S5-Q01 ~ S5-Q07

**自测清单**
1. 窗口函数能不能直接写在 `WHERE` 里？为什么？要怎么过滤排名？
2. 3 行并列第 1 时，RANK 和 DENSE_RANK 的下一个名次各是几？
3. `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` 遇到「3 月完全没有数据」时，滑动窗口里实际是哪几个月？

## 阶段 6 · 数据变更与事务（6 题 / 74 分）

**知识点**
- 变更三步：先 SELECT 确认影响行数 → 改 → 复核
- 主外键顺序：插入先主后子，删除先子后主
- `UPDATE ... FROM`（SQLite/PG）vs `UPDATE JOIN`（MySQL）
- 分批 DELETE、大事务拆分、删除不释放磁盘（需 VACUUM / OPTIMIZE）
- UPSERT 三方言；幂等写入
- 显式事务 `BEGIN / COMMIT / ROLLBACK` 保证多条语句的原子性
- CTAS（`CREATE TABLE AS SELECT`）会丢主键、索引、约束、默认值

**对应题目**：S6-Q01 ~ S6-Q06

**自测清单**
1. MySQL 8.0 之前，事务里执行 DDL 会怎样？（对比 SQLite/PG）
2. 幂等 UPDATE 的 WHERE 应该描述「目标状态」而不是「执行次数」，举一例。
3. 归档大表的正确顺序是什么？为什么不能先 DELETE？

## 阶段 7 · 建模与约束（5 题 / 69 分）

**知识点**
- 主键策略：自增整数 vs UUID vs 分布式 ID（涉及索引页分裂与顺序写）
- `NOT NULL` + `CHECK` 组合才有效（CHECK 对 NULL 放行）
- 外键四种删除行为：`RESTRICT / CASCADE / SET NULL / SET DEFAULT`
- 唯一约束 + UPSERT = 幂等地基；唯一索引允许多个 NULL
- **金额必须用 DECIMAL 或整数分**，不能用 FLOAT
- 三范式与反范式的适用边界（OLTP 到 3NF，OLAP 反而宽表更快）

**对应题目**：S7-Q01 ~ S7-Q05

**自测清单**
1. `products(category_id, price)` 之外还有单独的 `(category_id)` 索引，冗余吗？为什么？
2. `0.1 + 0.2 = 0.3` 在浮点里成立吗？`CAST(19.99*100 AS INT)` 是几？
3. 宽表 `order_flat` 存在什么异常？它应该出现在业务库还是分析库？

## 阶段 8 · 索引与执行计划（6 题 / 85 分）

**知识点**
- SQLite 计划术语：`SCAN` / `SEARCH` / `USING INDEX` / `USING COVERING INDEX` / `TEMP B-TREE`
  （对应 MySQL 的 `type=ALL/ref/range/index` + `Using index` + `Using filesort`，
  PG 的 `Seq Scan` / `Index Scan` / `Index Only Scan`）
- 最左前缀原则；等值列在前、范围列在后
- 覆盖索引消除回表（回表 = 随机 IO）
- 索引失效四因：函数包裹列、前置模糊匹配、类型不匹配、OR 混合
- `ORDER BY` 顺着索引可免排序（同序、同向、单表）
- 冗余索引识别；索引不是免费的（写放大、磁盘、优化器干扰）

**对应题目**：S8-Q01 ~ S8-Q06

**自测清单**
1. 已有 `(a, b, c)`，单独的 `(a)`、`(a,b)`、`(b)` 哪些冗余？
2. 为什么有时优化器故意放弃索引走全表扫描？
3. 线上要删一个索引，正确的三步流程是什么？

## 阶段 9 · 调优实战（4 题 / 57 分）

**知识点**
- 深分页：`OFFSET` 是 O(n)，keyset 游标是 O(log n)；支持行值比较 `(a,b) < (x,y)`
- `COUNT(*)` 与 `COUNT(1)` 等价；InnoDB 的 COUNT 慢是 MVCC 所致
- 相关子查询 → JOIN + GROUP BY 一次性完成；看 `DEPENDENT SUBQUERY` 决定是否改写
- TOP-N：`LIMIT` 要在「有合适索引」的前提下才能真正少干活

**对应题目**：S9-Q01 ~ S9-Q04

**自测清单**
1. keyset 分页的两个局限是什么？怎么支持跳页？
2. `COUNT(*)` 在无二级索引的大表上为什么慢？给出三种可行的优化手段。
3. 应用层用 ORM 的 `page/per_page` 参数分页，什么情况下必须改成游标（cursor）？

## 验收方式

1. **自动判分**：`python run.py progress` 看到阶段进度条全部填满，
   `python run.py diagnose` 里没有「薄弱」项，`python run.py wrong` 里错题清零。
2. **口述复核**：每道题回答三问 —— 这条 SQL 走什么执行路径？有没有第二写法？哪个更快为什么？
3. **迁移验证**：挑 3 道题，把答案改成 MySQL 8 语法，用 `references/cross-db-cheatsheet.md` 对照检查差异点。
4. **生产习惯**：任何 UPDATE/DELETE 前先 `SELECT COUNT(*)`；任何建索引前先想清楚它会被哪些查询用到。
